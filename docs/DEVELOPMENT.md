## Нова машина для розробки — чек-лист

Усі `.env`-файли git ігнорує, тому на кожній новій машині їх треба створити з шаблонів. Шаблони містять робочі dev-значення — достатньо скопіювати.

> ⚠️ `copy` — це PowerShell/cmd, у Git Bash / WSL її немає, там `cp`.

```powershell
# Backend (з папки backend/)
copy .env.example .env                                # SQLite, DEBUG=True — працює одразу
# → для PostgreSQL розкоментувати «Варіант 2» (БД rent_manager_dev) і вписати пароль

# Frontend (з папки frontend/)
copy .env.development.example .env.development        # dev: localhost:8001
copy .env.production.example .env.production          # збірка .exe для одного ПК
copy .env.network.example .env.network                # мережева збірка → вписати IP сервера!
```

Далі: `pip install -r requirements.txt` → `migrate` → `setup_groups` → `createsuperuser`, `npm install`, `npm run dev:all`.

> **Порти:** production-сервер (Waitress) — **8000**, dev-сервер (`dev:all` / `runserver`) — **8001**. Так вони не конфліктують на машині, де живе і те, і інше.

## Розгортання в мережі

Один ПК = **сервер** (Django + PostgreSQL), решта = **клієнти** (тільки `.exe`).

### На сервері

1. У `backend/.env` задати production-значення (див. [DEPLOY.md](DEPLOY.md), розділ «Безпека `.env`»): свій `SECRET_KEY`, `DEBUG=False`, `ALLOWED_HOSTS`, CORS, PostgreSQL.

2. Відкрити порт 8000 у firewall (від адміна):

    ```powershell
    New-NetFirewallRule -DisplayName "Django Rent Manager" `
      -Direction Inbound -Protocol TCP -LocalPort 8000 -Action Allow
    ```

3. Запустити Django через Waitress (production WSGI-сервер):

    ```powershell
    cd backend
    .\run_server.bat            # слухає 0.0.0.0:8000
    ```

    `run_server.bat` запускає `serve.py` (Waitress). **Не `runserver`** — то dev-інструмент.
    Запуск — лише через `.bat`, **не** через `powershell -ExecutionPolicy Bypass`: на такий виклик спрацьовує SOC (MITRE T1059.001).

4. Дізнатись IP: `ipconfig` → `192.168.x.x`.

### На клієнтах

Встановити зібраний `.exe`, який вказує на IP (або ім'я) сервера.

### Dev / prod розділені фізично

Якщо сервер і розробка — на одному ПК, їх **обов'язково** розділяти, щоб експерименти не зачепили реальні дані:

- **Prod** — окрема папка, чекаут гілки `main`, свій `.env` з бойовою БД (`DEBUG=False`), Waitress на 8000.
- **Dev** — робоча папка з гілкою `dev`, окрема БД (`rent_manager_dev`) у тому самому Postgres, `DEBUG=True`, `runserver 8001`.

## Збірка .exe

URL бекенду «запікається» в збірку через Vite (`VITE_API_URL`), тому є два режими:

```powershell
cd frontend

# Один ПК (Django на тому ж комп'ютері) — .env.production
npm run electron:build              # portable .exe
npm run electron:build:installer    # NSIS-інсталятор

# Мережа — .env.network (спочатку вписати IP сервера)
npm run electron:build:network
npm run electron:build:network:installer
```

Результат — у `frontend/release/`.

> Для NSIS-інсталятора потрібен Windows Developer Mode (Settings → System → For developers), інакше electron-builder не створить symlinks. Portable-версія працює без цього.

## Реліз нової версії

Авто-оновлення немає (LAN без інтернету) — клієнти отримують лише сповіщення. Три ручні кроки:

1. **Bump версії** у `frontend/package.json`
2. **Запис у `CHANGELOG`** на початку `frontend/src/lib/changelog.ts` — список у діалозі «Що нового»
3. **Підняти `LATEST_VERSION`** у `backend/.env` на сервері + перезапустити Waitress — старі клієнти побачать toast «вийшла нова версія»

Якщо в релізі є **міграції** — на сервері після `git pull` виконати `python manage.py migrate` **до** перезапуску Waitress. Спершу прогнати їх на копії бойової бази (у `rent_user` немає `CREATEDB` — копію робити під суперкористувачем Postgres).

Далі зібрати `.exe` і роздати клієнтам.

## Бізнес-правила детально

### Основний цикл роботи

1. Менеджер **генерує рахунки** за місяць або діапазон місяців — система створює порожні рахунки для всіх активних зв'язок договір↔послуга (і записи постачальників)
2. Менеджер вводить **споживання** (м³, кВт·год…) → довідкова колонка «Спожито» = `обсяг × тариф`. «Нараховано» саме не проставляється (з 1.5.0): його вносять свідомо або масово кнопкою «Нарахування»
3. Менеджер вводить **сплачено** (вручну або масово)
4. Бухгалтер **верифікує** рахунки
5. Бухгалтер **закриває період окремо по сутності** — «Орендарі» або «Постачальники». Записи закритої сутності редагує тільки адмін; бухгалтер може період знову відкрити

### Борг

**Наростаючий у межах року** (з 1.6.0): борг місяця = Σ (нараховано + корекція − сплачено) з січня по цей місяць. Грудень = «Заг. борг» за рік. З минулого року борг не переноситься (рішення клієнта). Рахується на фронті з даних місяців (`runningDebts` у `billing-utils.ts`), а не з серверного `debt_start` — той записується раз при генерації й застаріває після правок попередніх місяців.

### Сутності

- **Історія тарифів** (`ServiceRate`) — записи «значення + дата початку дії». Тариф місяця = запис, чинний на 1-ше число періоду; у рахунку тариф — **снапшот** на момент створення (зміна тарифу не зачіпає старі рахунки)
- **Договір відшкодування** (`ReimbursementContract`) — річний документ, що може покривати кілька договорів оренди (M2M). Періоди одного договору не перетинаються. Об'єднані договори виводяться в «Рахунках» окремими секціями з підсумками груп
- **Постачальник** (`Supplier`) — дзеркальна логіка: що установа сама платить постачальникам. Рядки — в тій самій таблиці після «Разом», далі підсумки й рядок «Різниця» (постачальник − орендарі)
- **Фонди** (з 1.6.0) — установа платить постачальнику з двох бюджетних фондів: **спеціального** (власні надходження — те, що відшкодовують орендарі) і **загального** (бюджет). Акт приходить однією сумою, бухгалтер вручну розписує її на два фонди. Тому на місяць — **два записи** (`SupplierBill.fund`)
- **Річний план фонду** (`SupplierFundPlan`) — сума й обсяг на рік по кожному фонду. Окрема таблиця, бо договір постачальника буває безстроковим, а план щороку свій
- **Замок періоду** (`PeriodLock`) — закриття — факт про пару «період + сутність». Замок орендарів записи постачальника **не блокує** (їх вносять заднім числом); місяць, закритий для постачальників, генерація пропускає

### Інваріанти даних

- Усі грошові поля — `DecimalField`, у API серіалізуються як **рядки**; обсяг/тариф — `DecimalField(18,9)`
- Округлення грошей — лише half-up: бек — `Decimal.quantize(..., ROUND_HALF_UP)`, фронт — `roundMoney()`
- `Bill.total_debt_end = (debt_start + accrued_amount + correction) − paid_amount`
- `unique_together`: `Bill (contract, service, period)`; `SupplierBill (supplier_contract, period, fund)`
- `BillingPeriod.is_closed` в API **не видаляти**, поки є клієнти зі старими Electron-збірками — вони читають саме це поле (тепер це property над замком орендарів)

## API ендпоінти

Базовий префікс `/api/`. Усі (крім `/api/auth/*`) вимагають `Authorization: Bearer <access_token>`.

### Авторизація

| Метод | URL                  | Опис                                                       |
| ----- | -------------------- | ---------------------------------------------------------- |
| POST  | `/api/auth/login/`   | username + password → access + refresh (з роллю в payload) |
| POST  | `/api/auth/refresh/` | refresh → новий access                                     |

### CRUD (DRF Router)

| URL                             | Ресурс                                                                                                  |
| ------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `/api/tenants/`                 | Орендарі                                                                                                |
| `/api/contracts/`               | Договори (фільтр `?tenant_id=`)                                                                         |
| `/api/reimbursement-contracts/` | Договори відшкодування (фільтр `?contract_id=`)                                                         |
| `/api/services/`                | Послуги (+ `current_rate` і найближча майбутня зміна тарифу)                                            |
| `/api/service-rates/`           | Історія тарифів (фільтр `?service_id=`)                                                                 |
| `/api/contract-services/`       | Зв'язки договір↔послуга (фільтри `?contract_id=`, `?service_id=`)                                       |
| `/api/periods/`                 | Розрахункові періоди (+ `locks`: стан замка по кожній сутності)                                         |
| `/api/bills/`                   | Рахунки (фільтри `?service_id=`, `?year=`, `?month=`, `?contract_id=`)                                  |
| `/api/suppliers/`               | Постачальники                                                                                           |
| `/api/supplier-contracts/`      | Договори постачальників (фільтри `?supplier_id=`, `?service_id=`)                                       |
| `/api/supplier-bills/`          | Записи постачальників (фільтри `?service_id=`, `?supplier_contract_id=`, `?year=`, `?month=`, `?fund=`) |
| `/api/supplier-fund-plans/`     | Річні плани фондів (фільтри `?service_id=`, `?supplier_contract_id=`, `?year=`)                         |

### Кастомні actions

| Метод | URL                            | Хто                    | Опис                                                                                                                              |
| ----- | ------------------------------ | ---------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| POST  | `/api/periods/generate-bills/` | Менеджер               | рахунки за `{year, month, month_to?, service_id?, update_rates?}` (+ записи постачальників); `update_rates` — лише бухгалтер/адмін |
| POST  | `/api/periods/{id}/close/`     | Бухгалтер              | закрити період; body `{"scope": "tenants" \| "suppliers"}`, без scope — орендарі                                                  |
| POST  | `/api/periods/{id}/reopen/`    | Бухгалтер              | відкрити період по тій самій сутності (інші замки не зачіпає)                                                                     |
| POST  | `/api/bills/{id}/verify/`      | Бухгалтер              | позначити перевіреним                                                                                                             |
| POST  | `/api/bills/{id}/unverify/`    | Бухгалтер              | зняти позначку                                                                                                                    |
| GET   | `/api/version/`                | будь-хто авторизований | остання роздана версія (`LATEST_VERSION` з `.env`) — для сповіщення про оновлення                                                 |

## Логування та бекап

### Логування

Middleware [rentals/middleware.py](../backend/rentals/middleware.py) пише кожен API-запит у `backend/logs/api.log`:

```
[2026-05-29 10:30:00] admin | 192.168.0.10 | PATCH /api/bills/5/ | 200 | 0.045s | {"paid_amount": "500.00"}
```

Файл ротується (10 МБ × 10 архівів). Паролі та токени в лог не потрапляють.

### Бекап

```powershell
python manage.py backup_db      # разовий бекап
.\backup_server.bat             # ручний бекап з записом у logs/backup.log
```

Авто-запуск (щодня о 23:00 і при вмиканні ПК) — див. [backend/AUTOSTART.md](../backend/AUTOSTART.md).
Бекапи: `backend/backups/backup_YYYY-MM-DD_HH-MM.sql.gz` (зберігаються 30 останніх).

## Глосарій

| Термін                     | Пояснення                                                                                                                  |
| -------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **Access / Refresh token** | access живе 30 хв і додається до кожного запиту; refresh — для отримання нового access без повторного входу                |
| **SWR**                    | бібліотека кешування запитів (stale-while-revalidate): кеш за URL-ключем, фонове оновлення                                 |
| **Розрахунковий період**   | місяць (рік + місяць); закривається окремо для кожної сутності                                                             |
| **Opening Balance**        | перенос боргу при генерації: `debt_start` нового рахунку = борг на кінець попереднього місяця (знімок, у таблиці не видно) |
| **Наростаючий борг**       | колонка «Борг»: Σ (нараховано + корекція − сплачено) з січня по місяць; рік стартує з 0                                    |
| **Фонд**                   | бюджетне джерело оплати постачальнику: спеціальний (відшкодування орендарів) або загальний (бюджет)                        |
| **Замок періоду**          | `PeriodLock` — період закрито для конкретної сутності, а не цілком                                                         |
| **Снапшот тарифу**         | тариф копіюється в рахунок при створенні; історія — у `ServiceRate`                                                        |
| **Верифікація**            | позначка бухгалтера, що рахунок перевірено                                                                                 |
| **portable .exe / NSIS**   | виконуваний файл без встановлення / інсталятор для Windows                                                                 |
